# STAYSCENE 스타일링 스튜디오 — 구현·검증 보고 (2026-11-23)

> **한 줄 요약:** 현장 사진 1~3장에 실제 제품 3D 모델을 놓고, 여러 시점에서 같은 위치로 합성하고, A/B 안을 버전 고정 링크로 고객에게 보내 선택·승인까지 받는 흐름이 브라우저에서 끝까지 동작합니다. **원본 사진 보존(마스크 밖 픽셀 차이 0)과 시점 간 위치 일치는 검증했고, '실물과 같은 사실감'은 아직 입증하지 못했습니다** — 실물 비교 사진과 범용 AI 기준선이 없어서입니다. 그래서 모든 결과의 공개 상태는 **'내부 테스트'** 입니다.

결과 사진 한 세트: [`docs/studio-results/`](studio-results/) (원본 · A안 · B안 × 3시점, `contact_sheet.jpg`), 재현 근거: [`docs/studio-results/manifest.json`](studio-results/manifest.json) (시점별 카메라, 에셋 버전·파일 해시, 배치·조명, 마스크 버전, QA, 입력 해시).

## 1. 대표님 질문에 대한 짧은 답

**① 어느 업체가 지금 어떤 작업에 실제로 쓸 수 있나?**
고객이 고른 소파의 **제조사 3D 모델(GLB)** 이 있고, 바닥이 보이는 방 사진(EXIF 초점거리 포함 원본)과 **줄자로 잰 기준점 4~6개**를 넣을 수 있는 인테리어 업체가, "이 자리에 A 소파 vs B 소파" **배치·크기 결정용 내부 검토 시안**을 만드는 데 쓸 수 있습니다. 위치·회전·치수를 바꾸면 모든 시점이 함께 바뀌고 버전·변경 요약이 남습니다. 외부 고객에게 '완성 사진처럼' 보낼 수준인지는 미검증입니다(③④).

**② ChatGPT 기준선보다 나았던 점 / 끝나지 않은 비교**
- 구조적으로 확인된 차이: (a) 원본 픽셀 보존이 **측정값 0**으로 보장됨(테스트에서 공급자가 사진 전체를 빨갛게 바꿔 보내도 허용 영역 밖은 원본 복원), (b) 같은 제품을 **여러 시점에 같은 월드 위치**로 놓음, (c) "30cm 이동·15° 회전" 같은 수정이 **수치로 재현**되고 변경 요약에 남음, (d) 승인 버전 고정·공유 철회.
- **미실행:** ChatGPT·이미지 편집 모델 기준선 실행(계정·키 없음), 사람 평가(심사자 0명). 평가 절차와 사례 정의는 [`samples/eval/cases.json`](../samples/eval/cases.json)에 준비됨. 따라서 "기준선보다 품질이 낫다"는 주장은 아직 할 수 없습니다.

**③ 어느 고객 사진을 받아도 괜찮다는 근거가 있나?**
없습니다. 검증된 범위는 다음뿐입니다.
- 사진: 실제 촬영 파노라마(Poly Haven *Small Empty Room 1*, CC0)에서 원근으로 잘라낸 3장. 모두 **같은 촬영 위치**(순수 회전)라 시차가 있는 다시점은 미검증.
- 렌즈: 15mm·18mm·30mm(35mm 환산), **왜곡 없는 핀홀**. 실제 광각 렌즈 왜곡은 보정하지 않음 → 화각 85° 이상이면 화면에 경고.
- 가구: 정확한 3D 모델이 있는 소파 2종(CC0 Poly Haven, 실제 판매 SKU 아님). 사진만 있는 제품은 정면 근처만 '외관 추정', 그 외 각도는 '추가 참조 필요'로 막음.
- 스케일: 샘플은 실측이 없어 문 높이 2.0m 가정 → **'추정' 상태**. 실측 기준점 + 검증점이 있어야 '실측 기준 확인'이 됩니다.

**④ '실물과 같은 수준'을 못 낸 장면과 다음에 필요한 것**
- 못 낸 것: 결과 세트 전체. 축소 화면에서는 그럴듯하지만, 100% 확대 시 B안(빅토리안 소파)은 조명이 평평해 CG처럼 보이고, 샘플 방이 작아(2.8m×4.0m) 카메라가 소파와 0.5~1m 거리라 구도가 극단적입니다. 벽에는 그림자가 지지 않습니다(섀도 캐처가 바닥면만).
- 직접 시험한 것: 3D 경로(three.js 셰이더·VSM 그림자·접지 그림자·사진 기반 환경광·노이즈/초점 맞춤), 가림·보호 마스크, 이미지 편집 API 경계 보정(가짜 공급자로 복원 로직만 검증).
- 다음 진전에 필요한 것: **같은 삼각대 위치의 빈 방 / 실제 소파 배치 사진 쌍 2~3세트**(자연광 거실, 혼합광 숙소, 광각 가장자리), 해당 소파의 제조사 3D 모델, 이미지 편집 API 키(경계 보정 실계정 확인), 건축사진 작업자 2명의 블라인드 평가. 오프라인 경로 추적 렌더러(Blender/Cycles)는 이 환경에 설치하지 않았습니다 — 실사감 개선의 다음 후보이며 워커 인터페이스(레이어 PNG 반환)는 교체 가능하게 분리해 두었습니다.

**⑤ 내부 사용자와 외부 업체는 어디서 시작하나? 테스트 계정·운영 연결은?**
- 업체: `/studio` 로그인 → **샘플 프로젝트 열기** 또는 새 프로젝트. 가입은 운영자가 만든 초대 링크(`/studio/join/<토큰>`)로만.
- 스테이신 내부: 같은 편집기 + `/studio/ops`(상담 요청, 포함 자료만 열람, 렌더 실패 원인, 사용량, 업체 초대).
- 테스트에 쓴 계정·데이터: 자동 테스트는 임시 DB의 가짜 업체 2곳 + 운영자 1명, 로컬 확인은 `vendor@test.local`/`ops@stayscene.local`(로컬 DB에만 존재). 실제 고객 사진은 사용하지 않았습니다.
- 운영 연결에 필요한 것: 호스팅 계정(영구 디스크 포함), `DATABASE_URL`, `SESSION_SECRET`, 첫 운영자 계정 생성(`npm run studio:create-user`), (선택) `OPENAI_API_KEY`. 기존 OFFICE 로그인과는 **분리된 계정**입니다(통합 지점은 7절).

**⑥ 한 시안을 만들고 고치는 데 걸린 시간과 비용**
브라우저 자동 실행 기준(사람 손 시간이 아니라 스크립트 실행 시간, 이 컨테이너의 CPU 렌더):

| 단계 | 시간 |
|---|---|
| 프로젝트 생성 + 사진 업로드 | 1.4초 |
| 기준점 6개 좌표 입력·클릭 → 보정 '추정' | 3.6초(자동 입력) — 사람이 하면 첫 사용 시 수 분 예상, **미측정** |
| 가구 배치 + 치수·위치·회전 수정 | 약 17초 |
| 최종 합성 1시점(2400×1600) | **28초** (GPU 없는 SwiftShader) |
| A·B 각 3시점 | 167초 |
| 공유 → 고객 승인 → 승인 후 수정(v2) | 약 15초 |

비용: 3D 렌더는 외부 API를 쓰지 않아 **호출 비용 0원**(서버 CPU 시간만). 이미지 편집 API는 키가 없어 미실행 → 비용 미측정. **실행하지 못한 것:** 사람 작업 시간 측정(파일럿 미실시 — `studio_pilot_logs`·`edit_time` 기록 기능만 구현), 기준선 비교.

**⑦ 공개 범위 판단**

| 외부 업체에 열어도 됨 | 내부 검수로만 | 추가 현장 테스트 필요 |
|---|---|---|
| 프로젝트·사진 업로드·제품 등록, 기준점 보정(상태·부족한 입력 안내 포함), 배치 미리보기·A/B 안·버전, 공유 링크(배치 시뮬레이션 표시·만료·철회), 상담 요청 | 최종 합성 이미지의 고객 전달(현재 상태 '내부 테스트'), 사진만 있는 제품의 합성, AI 경계 보정 | 실사감(실물 쌍 비교), 실제 광각 렌즈, 혼합광·창 반사·금속/유리 재질, 다시점 시차 사진, 사람 작업 시간 |

## 2. 실행 방법

Node.js 20+, PostgreSQL 14+, (최종 합성용) Chromium.

```bash
cp .env.example .env
```

```bash
npm install
```

```bash
npm run db:migrate
```

스테이신 운영자 계정:

```bash
STUDIO_EMAIL=you@stayscene.kr STUDIO_NAME=대표 STUDIO_PASSWORD='10자 이상' STUDIO_WORKSPACE=스테이신 STUDIO_OPS=true npm run studio:create-user
```

테스트 업체 계정(또는 운영 화면에서 초대 링크 발급):

```bash
STUDIO_EMAIL=vendor@example.com STUDIO_NAME=실장 STUDIO_PASSWORD='10자 이상' STUDIO_WORKSPACE=테스트인테리어 npm run studio:create-user
```

```bash
npm run dev
```

개발 중에는 `http://localhost:5173/studio`, 빌드 후(`npm run build && npm start`)에는 `http://localhost:3000/studio`. 렌더 워커는 API 프로세스 안에서 함께 돕니다(`STUDIO_RENDER_IN_PROCESS=true`).

| 화면 | 경로 |
|---|---|
| 프로젝트 목록·샘플 열기 | `/studio` |
| 편집기(방 단위) | `/studio/r/<roomId>` |
| 가구 제품 등록·버전 | `/studio/assets` |
| 운영(상담·사용량·초대) | `/studio/ops` (운영자만) |
| 고객 공유(로그인 없음, 모바일) | `/s/<토큰>` |
| 업체 가입 | `/studio/join/<초대 토큰>` |

### 환경변수 (스튜디오 추가분)

| 이름 | 필수 | 목적 |
|---|---|---|
| `STUDIO_STORAGE_DIR` | ✔(운영) | 원본·렌더 비공개 저장 경로. 운영은 영구 디스크(`/var/data/studio`) |
| `STUDIO_CHROMIUM_PATH` | 권장 | 3D 렌더 워커 Chromium. Docker 이미지는 `/usr/bin/chromium` |
| `STUDIO_RENDER_IN_PROCESS` | 선택 | `false`면 API에서 렌더하지 않음(별도 워커 분리 시) |
| `STUDIO_MAX_UPLOAD_MB` / `STUDIO_MAX_PHOTO_MP` | 선택 | 업로드 크기(기본 40MB) / 픽셀 수(기본 60MP) |
| `STUDIO_SHARE_DAYS` | 선택 | 공유 링크 기본 만료일(14) |
| `OPENAI_API_KEY` | 선택 | 이미지 편집 API 경계 보정. 없으면 버튼 비활성 |
| `STUDIO_IMAGE_MODEL` | 선택 | 기본 `gpt-image-2.5-sunburst` (`gpt-image-1`은 2026-10-23 종료 — 공식 문서). 실계정 확인 필요 |
| `STUDIO_AI_EDIT_COST_USD` | 선택 | AI 보정 1회 비용 기록용 단가 |

조건: 클릭 오차를 ±1px로 흉내 낸 정답 좌표, 기준점은 파노라마에서 육안 지정. 첫 목표(중앙값 10px) 안이지만 **표본 1개 방, 시뮬레이션 클릭**입니다. 기준점이 거의 일직선(커튼 끝단)이면 두 카메라가 똑같이 잘 맞는 상황이 실제로 발생했고, 이를 공분산 기반 '불확실' 경고로 잡도록 고쳤습니다.

## 4. 구조와 기술 선택

- **같은 저장소·같은 서버·같은 DB, 분리된 모듈.** 기존 OFFICE(내부 상담·정산 앱)와 화면·계정·세션 쿠키·테이블을 분리했습니다(`studio_*`, `/api/studio/*`, `/studio`). 외부 업체 계정이 내부 상담 데이터에 닿을 경로 자체를 없애기 위함. 비밀번호 해시·DB 풀·마이그레이션·Fastify는 재사용.
- **3D 경로 우선, 렌더러 = three.js.** 편집기 미리보기와 서버 최종 렌더가 **같은 `scene.ts`** 를 씁니다(미리보기와 결과의 형상·재질 불일치 방지). 서버는 헤드리스 Chromium(SwiftShader WebGL2)에서 원본 해상도로 2048px 타일 렌더 → 가구 RGBA(프리멀티플라이드)·그림자 알파 레이어. Blender/Cycles는 이 환경에 없어 채택하지 않았고, 워커는 "레이어 PNG를 돌려주는" 인터페이스라 교체 가능합니다.
- **합성은 서버가 결정.** 변경 허용 마스크 = (가구 알파 ∪ 그림자) − 전경 가림 − 보호 영역. 그 밖은 원본 바이트를 복사하고, 저장한 무손실 PNG를 다시 디코드해 독립 검증합니다. 노이즈는 원본에서 추정(라플라시안 MAD), 초점 흐림·노출·화이트밸런스는 시점별 값으로 가구 레이어에만 적용.
- **카메라 보정**(`src/shared/studio/geometry.ts`, 의존성 없음): 바닥 호모그래피(정규화 DLT) → 초점 추정 → 자세 분해 → Levenberg–Marquardt(회전·위치·초점) + 다중 시작. 일렬·좁은 분포·점 부족·비정상 화각/카메라 높이·높은 잔차·검증점 오차·**불확실성(클릭 1.5px 가정 공분산)** 을 이슈로 반환. 상태: 미보정/추정/실측 기준 확인/실패.
- **월드 상태 하나.** 배치는 방 단위 월드 좌표(m)에 한 번만 저장, 시점별 픽셀은 투영으로 계산. 드래그는 포인터 광선과 바닥 평면의 교점.
- **버전.** 에셋 버전 불변(파일 교체 = 새 버전), 안 버전은 초안만 수정 가능·공유/승인/저장 시 잠김, 변경 요약은 그 버전의 시작 상태 대비 실제 값. 렌더 작업은 입력 스냅샷(보정 rev·마스크 rev·에셋 버전·파일 해시·렌더러 버전)의 해시로 중복 식별.
- **파일 업로드**는 멀티파트 없이 원본 바이트 그대로 받아 변경 없이 보관(원본), 방향·sRGB 정규화 PNG(마스터), 1600px 미리보기를 따로 저장. 공개 파일(전달용 JPEG)은 메타데이터·위치 정보 제거.

주요 파일: `src/server/studio/`(routes, renderJobs, renderer, images, calibration, aiEdit, glb, sample), `src/web/studio/`(editor, pages, render/scene.ts), `src/shared/studio/`, `004_studio.sql`, `samples/`.

## 5. 작업 중 내린 결정 기록 (되돌릴 수 있음)

1. **샘플 사진 = 실제 촬영 파노라마의 원근 크롭(CC0).** 첨부 예정이던 화면 6장은 이 세션에 들어오지 않았고, 출처 불명 사진·생성 이미지는 쓰지 않았습니다. 정답 카메라를 알 수 있어 기하 검증에 유리하지만 시차 없는 다시점이라는 한계가 있습니다.
2. **샘플 가구 = Poly Haven CC0 소파 2종.** "검증된 3D 에셋"의 대역. 실제 판매 SKU가 아님을 카탈로그·제품 목록에 표기.
3. **스케일 근거 = 문 높이 2.0m 가정**(손잡이 높이 0.93m로 교차 확인). 실측이 아니므로 '추정'.
4. **EXIF 35mm 환산 초점을 기본 사용.** 기준점만으로 초점이 불확실한 경우가 실제로 생겨서. 크롭본처럼 EXIF가 없으면 초점 입력을 요청.
5. **렌즈 왜곡 미보정(핀홀).** 미리보기·렌더·마스크 전체에 같은 왜곡을 적용하는 작업이 커서 보류, 광각에서 경고만 표시.
6. **실물 비교 전에는 모든 결과를 '내부 테스트'로.** 가림이 가구의 절반 이상을 덮으면 '수동 정밀 합성 필요', 사진 제품의 각도 부족은 '추가 참조 필요'.
7. **이미지 편집 API는 경계 띠만.** 공식 문서상 마스크가 '가이드'라 바깥도 바뀔 수 있음 → 가구 내부(3D 렌더)와 마스크 밖(원본)은 항상 복원, 3D 렌더 원본은 비교 기준으로 보존. 작업공간 한도 기본 0(운영자가 열어야 사용).
8. **URL 자동 수집 없음.** 출처 링크는 기록용.
9. **사진 교체 시 이전 클릭점은 '제안'으로만.** 수학은 픽셀 내용을 보지 못하므로 새 사진에서 자동 확정하면 잘못된 보정이 '정상'으로 보일 수 있음.

## 6. 알려진 한계·위험

- 렌더 시간: GPU 없는 서버에서 2400×1600 한 시점 약 25~30초, 첫 미리보기도 저사양 PC에서는 수 초 걸릴 수 있음.
- 섀도 캐처는 바닥만 → 벽·기존 집기에 드리우는 그림자 없음. 반사(유리·금속), 반투명 재질, 창 직사광은 별도 실패 유형으로 아직 다루지 않음.
- 사진 기반 제품은 평면(빌보드) + 보이지 않는 상자 그림자 → 배치 미리보기 수준.
- 다중 가구 충돌·방 경계는 바닥 사각형 기준 경고만(벽 형상 미모델링).
- 파일 저장은 로컬 디스크 어댑터만 구현(S3 호환 어댑터는 `storage.ts` 교체 지점).
- 공유 링크 접근은 토큰 기반(만료·철회 지원). 링크를 받은 누구나 볼 수 있으므로 비밀번호 보호는 미구현.
- Docker 이미지(시스템 Chromium 포함)는 아래 '배포'에 적은 범위까지만 확인.

## 7. 기존 사이트·운영과의 통합 지점

- 기존 OFFICE와 같은 서버·DB에 탑재(`studioPlugin`). 기존 51개 테스트 영향 없음.
- 계정 통합: 지금은 별도(`studio_users`). 스테이신 직원이 OFFICE 계정으로 들어오게 하려면 `studio/auth.ts`의 세션 해석에 OFFICE 세션 → 내부 작업공간 매핑을 추가.
- 상담 요청 → OFFICE 문의/작업으로 넘기기, 외부 메시지 발송: 미연결(운영 화면에 표시만).
- 공개 소개 페이지: 미구현(로그인 화면에 한 줄 소개만). 스테이신 홈페이지가 다른 저장소라면 `/studio` 링크로 연결.

## 8. 배포

`Dockerfile`이 시스템 Chromium·한글 글꼴을 설치하고 렌더 번들(`dist-render/`)·샘플 에셋을 포함합니다. `render.yaml`에 영구 디스크(`/var/data`, 20GB)와 `STUDIO_STORAGE_DIR`를 추가했습니다(디스크는 유료 인스턴스 필요). 운영 배포는 호스팅 계정이 없어 하지 않았습니다.

검증한 범위(이 컨테이너, 운영 주소 아님):
- `npm run build` → `NODE_ENV=production node dist-server/server/index.js`, 새 DB: 마이그레이션 자동 적용, `/api/health` 200, `/studio`·`/s/<토큰>`·기존 OFFICE `/` 200, 샘플 열기 → 프로세스 내 렌더 워커가 **미리 빌드된 렌더 번들**로 1시점 렌더 완료(24.5초, 마스크 밖 변경 0).
- **Docker 이미지 빌드는 미완료:** 이 샌드박스에서 Docker Hub가 429(요청 과다)를 돌려주고, 빌드 컨테이너가 외부 DNS를 직접 풀지 못합니다. 첫 시도에서 런타임 단계의 Debian `chromium`(156) 패키지 설치까지는 진행됨을 확인했습니다. 운영 플랫폼(Render 등)에서 첫 빌드 후 `/studio` 샘플 렌더 1회로 확인이 필요합니다. 시스템 Chromium과 `playwright-core` 1.65의 호환은 같은 방식(CDP)이라 문제없을 것으로 보지만 **미검증**입니다.
